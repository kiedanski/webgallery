<project_specification>
  <project_name>WebGallery — F-Droid Photo Gallery for Tilde WebDAV</project_name>

  <overview>
    WebGallery is a minimal, F-Droid-compatible Android gallery app that displays photos and videos
    served from a Tilde personal cloud server via WebDAV. The app downloads all 256px WebP thumbnails
    for offline grid browsing, caches opened full-resolution images with a configurable LRU cache, and
    supports marking photos/videos as favorites for permanent offline access. V0 shows only server
    content — no local device photos.

    Tilde (https://github.com/user/tilde) organizes photos by year/month under /dav/photos/, generates
    256px square-crop WebP thumbnails accessible via symlinks at _thumbnails/{year}/{month}/{filename}.webp,
    and serves originals at {year}/{month}/{original_filename}. Authentication is HTTP Basic Auth
    (username + password). The app discovers content via standard WebDAV PROPFIND operations.

    Design goals: minimal APK size (&lt;15 MB), low memory footprint (&lt;200 MB during browsing),
    offline-first thumbnail browsing, and clean Material 3 UI with dark mode support.
  </overview>

  <architecture>
    <pattern>MVVM with unidirectional data flow (ViewModel → StateFlow → Compose UI)</pattern>

    <di_strategy>
      Manual constructor injection via AppContainer singleton. AppContainer is created in
      WebGalleryApp.onCreate() and holds all repository, client, and database instances.
      ViewModels receive dependencies via a custom ViewModelFactory.
    </di_strategy>

    <concurrency>
      Kotlin Coroutines throughout. Sync operations run on Dispatchers.IO. UI state is
      exposed via StateFlow and collected with collectAsStateWithLifecycle. Room queries
      return Flow for reactive updates.
    </concurrency>

    <server_setup>
      <title>Server Connection Setup</title>
      <user_flow>
        1. App launches for the first time (setup_complete = false in DataStore)
        2. SetupScreen is shown — no bottom navigation bar visible
        3. User sees:
           - App icon and name "WebGallery" centered at top
           - Server URL text field (keyboard type: URI, placeholder: "https://tilde.example.com")
           - Username text field (keyboard type: text)
           - Password text field (keyboard type: password, with visibility toggle icon)
           - "Connect" button (full width, primary filled style)
        4. User fills in all three fields and taps "Connect"
        5. Button shows CircularProgressIndicator, all fields become disabled
        6. App sends PROPFIND to {server_url}/dav/photos/ with Depth: 0 and Basic Auth header
        7. On HTTP 207 Multi-Status:
           - Credentials saved to EncryptedSharedPreferences
           - setup_complete set to true in DataStore
           - Navigate to GalleryScreen (replaces SetupScreen in back stack)
           - Initial thumbnail sync begins automatically
        8. On HTTP 401 Unauthorized:
           - Show inline error below button: "Invalid username or password"
           - Re-enable fields and button
        9. On connection timeout / DNS failure / other network error:
           - Show inline error: "Cannot reach server. Check the URL and try again."
           - Re-enable fields and button
        10. On subsequent app launches: skip SetupScreen, go directly to GalleryScreen
      </user_flow>
    </server_setup>

    <thumbnail_sync>
      <title>Thumbnail Discovery, Download, and Incremental Sync</title>
      <trigger>Automatically on every app open (after setup). Also triggered by pull-to-refresh.</trigger>

      <sync_algorithm>
        Phase 1 — Directory Discovery:
          1. PROPFIND /dav/photos/_thumbnails/ with Depth: 1
          2. Parse response → extract year directory hrefs (e.g., "2023/", "2024/", "2025/")
          3. Process years in reverse order (newest first, so recent photos appear quickly)
          4. For each year: PROPFIND /dav/photos/_thumbnails/{year}/ with Depth: 1
          5. Parse → extract month directory hrefs (e.g., "01/", "02/", ..., "12/")
          6. Process months in reverse order within each year

        Phase 2 — Change Detection (per month directory):
          1. For each {year}/{month}/ pair, look up SyncStateEntity by directory_path
          2. If SyncStateEntity exists and stored ETag matches the directory ETag from Phase 1: skip this month (no changes)
          3. If ETag differs, no record exists, or ETag is null: proceed to Phase 3

        Phase 3 — Thumbnail and Original Discovery (per changed month):
          1. PROPFIND /dav/photos/_thumbnails/{year}/{month}/ with Depth: 1
             → List of thumbnail files: [{href: "_thumbnails/2024/03/IMG_1234.webp", etag, size, lastModified}, ...]
          2. PROPFIND /dav/photos/{year}/{month}/ with Depth: 1
             → List of original files: [{href: "2024/03/IMG_1234.jpg", contentType: "image/jpeg", size: 4500000, etag, lastModified}, ...]
          3. Match each thumbnail to its original by filename stem:
             - Thumbnail stem: "IMG_1234" (strip ".webp" from "IMG_1234.webp")
             - Original stem: "IMG_1234" (strip ".jpg" from "IMG_1234.jpg")
             - Match when stems are equal
          4. For matched pairs, determine media_type from original's contentType:
             - contentType starts with "image/" → MediaType.PHOTO
             - contentType starts with "video/" → MediaType.VIDEO
          5. Orphaned thumbnails (no matching original): skip, do not insert into DB
          6. Originals without thumbnails: skip (thumbnails may not be generated yet)

        Phase 4 — Database Upsert:
          1. For each matched thumbnail-original pair:
             - If photo not in DB (by remote_thumbnail_path): INSERT with thumbnail_downloaded = false
             - If photo already in DB and etag changed: UPDATE etag, file_size, last_modified
             - If photo already in DB and etag unchanged: no-op
          2. Photos in DB for this month but no longer found on server: set is_deleted = true
          3. Update SyncStateEntity for this month directory with new ETag and current timestamp

        Phase 5 — Thumbnail Download:
          1. Query DB for all photos where thumbnail_downloaded = false AND is_deleted = false
          2. Download each with bounded concurrency (Semaphore, max 4 parallel downloads):
             GET /dav/photos/_thumbnails/{year}/{month}/{filename}.webp
          3. Save to: {context.cacheDir}/thumbnails/{year}/{month}/{filename}.webp
          4. On success: update PhotoEntity — thumbnail_downloaded = true, local_thumbnail_path = saved absolute path
          5. On failure (network error): skip, will retry on next sync
          6. Emit progress via SyncStatus.Syncing(currentCount, totalCount) after each download

        Phase 6 — Completion:
          1. Set SyncStatus to Complete
          2. Hide sync indicator after 2-second delay
      </sync_algorithm>

      <error_handling>
        - Network error during directory discovery: emit SyncStatus.Error("Sync failed — showing cached photos"), stop sync, show toast
        - Network error during individual thumbnail download: skip that thumbnail, continue with others
        - Server returns 401 during sync: emit SyncStatus.Error("Authentication failed"), stop sync
        - Sync is cancellable: if user navigates away or app is backgrounded, cancel coroutine scope
      </error_handling>

      <performance_notes>
        - Process newest months first so the user sees recent photos quickly
        - Gallery grid updates reactively via Room Flow as thumbnails are downloaded
        - ETag-based skip means incremental sync of a stable collection completes in seconds
        - OkHttp connection pooling reuses TCP connections across sequential PROPFIND requests
      </performance_notes>
    </thumbnail_sync>

    <cache_management>
      <title>Cache and Storage Management</title>

      <storage_layout>
        Thumbnails:     {context.cacheDir}/thumbnails/{year}/{month}/{filename}.webp
        Full-image LRU: {context.cacheDir}/fullsize/{year}/{month}/{original_filename}
        Favorites:      {context.filesDir}/favorites/{year}/{month}/{original_filename}
      </storage_layout>

      <thumbnail_cache>
        - All thumbnails are downloaded and kept indefinitely
        - NOT subject to LRU eviction
        - NOT counted against the configurable cache limit
        - Can be cleared manually from Settings (triggers re-download on next sync)
        - Typical size: 5–15 KB per thumbnail (256px WebP)
      </thumbnail_cache>

      <fullsize_cache>
        - LRU eviction policy based on last-access time
        - Configurable max size: user selects from presets (200 MB, 500 MB, 1 GB, 2 GB, 5 GB, Unlimited)
        - Default: 500 MB
        - After each full-image download: check total fullsize cache size
        - If over limit: evict least-recently-accessed files until under limit
        - On eviction: delete file, set local_full_path = null in PhotoEntity
        - Favorites are stored in a separate directory and never evicted from fullsize cache
        - Can be cleared manually from Settings
      </fullsize_cache>

      <favorites_storage>
        - Permanently stored in context.filesDir (survives cache clearing)
        - NOT subject to LRU eviction
        - NOT counted against the configurable cache limit
        - Removed only when user unfavorites an individual photo/video
        - No bulk clear — user must unfavorite individually
      </favorites_storage>

      <cache_accounting>
        ImageCacheManager tracks:
        - Total thumbnail cache size (sum of files in thumbnails/ directory tree)
        - Total fullsize cache size (sum of files in fullsize/ directory tree)
        - Total favorites size (sum of files in favorites/ directory tree)
        - Sizes calculated by walking directory trees and summing file lengths
        - Recalculated on demand (when Settings screen is opened)
      </cache_accounting>
    </cache_management>

  <webdav_operations>
    <overview>
      All WebDAV requests target {server_url}/dav/photos/ as the base path.
      All requests include an Authorization header: "Basic " + Base64(username + ":" + password).
      The WebDAV client uses OkHttp and parses responses with Android's built-in XmlPullParser.
    </overview>

    <operations>

      <connection_test>
        Purpose: Validate server URL and credentials during setup
        Method: PROPFIND
        URL: {server_url}/dav/photos/
        Request headers:
          - Authorization: Basic {base64_credentials}
          - Depth: 0
          - Content-Type: application/xml; charset=utf-8
        Request body:
          &lt;?xml version="1.0" encoding="UTF-8"?&gt;
          &lt;d:propfind xmlns:d="DAV:"&gt;
            &lt;d:prop&gt;
              &lt;d:resourcetype/&gt;
            &lt;/d:prop&gt;
          &lt;/d:propfind&gt;
        Expected response: HTTP 207 Multi-Status
        Error responses:
          - 401: Invalid credentials
          - Connection refused / timeout: Server unreachable
      </connection_test>

      <list_directory>
        Purpose: Discover directory contents (year dirs, month dirs, files)
        Method: PROPFIND
        URL: {server_url}/dav/photos/{path}/
        Request headers:
          - Authorization: Basic {base64_credentials}
          - Depth: 1
          - Content-Type: application/xml; charset=utf-8
        Request body:
          &lt;?xml version="1.0" encoding="UTF-8"?&gt;
          &lt;d:propfind xmlns:d="DAV:"&gt;
            &lt;d:prop&gt;
              &lt;d:displayname/&gt;
              &lt;d:getcontenttype/&gt;
              &lt;d:getcontentlength/&gt;
              &lt;d:getetag/&gt;
              &lt;d:getlastmodified/&gt;
              &lt;d:resourcetype/&gt;
            &lt;/d:prop&gt;
          &lt;/d:propfind&gt;
        Expected response: HTTP 207 Multi-Status with DAV:multistatus XML body
        Parsing rules:
          - Each &lt;d:response&gt; element represents one resource
          - First response is always the requested directory itself — skip it
          - &lt;d:href&gt; contains the resource path (may be relative or absolute)
          - &lt;d:resourcetype&gt; containing &lt;d:collection/&gt; child → directory
          - &lt;d:resourcetype/&gt; (empty/self-closing) → file
          - &lt;d:getcontenttype&gt; → MIME type string (for files only)
          - &lt;d:getcontentlength&gt; → file size as string, parse to Long
          - &lt;d:getetag&gt; → ETag string, strip surrounding quotes if present
          - &lt;d:getlastmodified&gt; → HTTP date string (RFC 7231 format)
          - Normalize href: strip {server_url}/dav/photos/ prefix to get relative path
      </list_directory>

      <download_file>
        Purpose: Download thumbnails, full-resolution images, and videos
        Method: GET
        URL: {server_url}/dav/photos/{relative_path}
        Request headers:
          - Authorization: Basic {base64_credentials}
        Expected response: HTTP 200 with binary body
        Implementation:
          - Stream response body directly to FileOutputStream (never buffer entire file in memory)
          - Use OkHttp response.body.source() with Okio buffered sink
          - Write to a temporary file first, rename to final path on success (atomic write)
          - Delete temporary file on failure
          - Report download progress via callback for large files (videos)
      </download_file>

    </operations>

    <xml_response_format>
      Example PROPFIND response (Depth: 1 on a month directory):

      &lt;?xml version="1.0" encoding="UTF-8"?&gt;
      &lt;d:multistatus xmlns:d="DAV:"&gt;
        &lt;d:response&gt;
          &lt;d:href&gt;/dav/photos/_thumbnails/2024/03/&lt;/d:href&gt;
          &lt;d:propstat&gt;
            &lt;d:prop&gt;
              &lt;d:resourcetype&gt;&lt;d:collection/&gt;&lt;/d:resourcetype&gt;
            &lt;/d:prop&gt;
            &lt;d:status&gt;HTTP/1.1 200 OK&lt;/d:status&gt;
          &lt;/d:propstat&gt;
        &lt;/d:response&gt;
        &lt;d:response&gt;
          &lt;d:href&gt;/dav/photos/_thumbnails/2024/03/IMG_1234.webp&lt;/d:href&gt;
          &lt;d:propstat&gt;
            &lt;d:prop&gt;
              &lt;d:displayname&gt;IMG_1234.webp&lt;/d:displayname&gt;
              &lt;d:getcontenttype&gt;image/webp&lt;/d:getcontenttype&gt;
              &lt;d:getcontentlength&gt;12345&lt;/d:getcontentlength&gt;
              &lt;d:getetag&gt;"a1b2c3d4"&lt;/d:getetag&gt;
              &lt;d:getlastmodified&gt;Mon, 01 Mar 2024 12:00:00 GMT&lt;/d:getlastmodified&gt;
              &lt;d:resourcetype/&gt;
            &lt;/d:prop&gt;
            &lt;d:status&gt;HTTP/1.1 200 OK&lt;/d:status&gt;
          &lt;/d:propstat&gt;
        &lt;/d:response&gt;
      &lt;/d:multistatus&gt;

      Parser must handle:
      - Multiple &lt;d:response&gt; elements
      - &lt;d:resourcetype&gt; with or without &lt;d:collection&gt; child
      - Missing or empty properties (nullable fields in DavResource)
      - Both relative and absolute hrefs
      - Quoted and unquoted ETags
      - Namespaced and non-namespaced XML (some servers vary)
    </xml_response_format>
  </webdav_operations>
